> 📌 版本：v1.0
> 🎯 規劃日期：2026-07-27
> 👤 規劃者：高粱（QA）
> 📌 現況基準：v0.2（2026-07-22）

## 一、使用者旅程分析

### 1.1 典型使用者故事

```
作為一個遊客，我想：
1. 輸入「我想去東京，5天4夜，要有淺草寺和晴空塔」
2. 系統自動生成「最佳路線」，告訴我每天幾點出門、怎麼搭車
3. 每個景點附近有「好吃的」，而且符合我的預算和口味
4. 能夠自己調整行程順序
5. 知道每家餐廳大約多少錢、要不要排隊、有沒有優惠
```

### 1.2 現有系統問題地圖

```
【輸入層】使用者在決定去哪裡之前，需要自己想清楚很多事
         → 不知道要填「必經車站」是什麼意思
         → 景點、車站名稱陌生，不知道要輸入什麼
         → 8個車站欄位太多，一般旅客不會有這麼明確的需求

【生成層】系統是「模板+填充」，不是真正的「路線規劃」
         → 使用者選的景點被亂塞進模板，不是按路線串起來
         → 每天5個時段機械化分配，忽略景點之間的移動時間
         → 景點先後順序沒邏輯，可能浪費一半時間在交通上

【用餐層】餐廳推薦等於「填空」，不是「推薦」
         → 同一類型餐廳連續出現（連吃兩餐燒肉）
         → 早餐/午餐/晚餐沒有風格區分
         → 沒有價格、排队、預訂需求的資訊

【輸出層】行程輸出後，使用者只能看、不能改
         → 系統說了算，使用者沒有掌控感
         → 連結太多、太雜，不知道哪個重要
         → 不知道每個地方要待多久、幾點要出門
```

## 二、核心問題清單

### 2.1 行程規劃層（最高優先）

| # | 問題 | 使用者痛點 | 技術根因 |
|---|------|-----------|---------|
| P1 | **模板綁死行程結構** | 使用者的選擇被「盡量塞入」模板，景點先後順序由模板決定，不是由路線邏輯決定 | `buildNormalDay` 完全依賴 `itineraries[day_key].activities` 結構 |
| P2 | **無視景點間移動時間** | 早上在淺草、下午在澀谷，中間一小時浪費在路上，但行程看不出來 | `buildNormalDay` 只有 `zone` 概念，沒有 `lat/lng` 距離計算 |
| P3 | **每天5時段機械分配** | 中午12:00~14:00一定吃飯、14:00~17:00一定逛，無視實際距離和排隊時間 | 時段是固定的，與景點實際 `stay_duration` 無關 |
| P4 | **抵達日/離開日邏輯錯誤** | 最後一天中午就結束，但很多人是晚上機票 | `buildSpecialDay` 只看 `day_key` 是否含 `arrival/departure`，但模板通常只有一個 arrival day |
| P5 | **同行人數完全無功能** | 團體旅遊需要知道餐廳能不能接待、需不需要預約，但輸入了沒用 | `state.travelers` 有值但行程生成邏輯完全沒用到 |

### 2.2 用餐安排層（高優先）

| # | 問題 | 使用者痛點 | 技術根因 |
|---|------|-----------|---------|
| F1 | **餐廳類型缺乏多樣性** | 早上吃甜點、午餐吃拉麵、晚餐吃燒肉——系統可能連續推薦同類型 | `mealsByZone` 只用 zone 分桶，沒有考慮 `sub_category` 多樣性 |
| F2 | **沒有用餐時段風格區分** | 早餐可能只是便利商店、晚餐是正式餐廳，但系統一視同仁 | 所有 meal slot 都是 `type='meal'`，沒有 sub_type 區分早/午/晚 |
| F3 | **缺少排隊/預訂資訊** | 推薦了一個要排隊2小時的店，行程完全被打亂 | `need_reservation` 欄位有值，但渲染層沒用到 |
| F4 | **沒有價格資訊** | 不知道這餐要花多少錢，無法控制旅遊預算 | `meals` 表沒有 `price_range` 欄位 |
| F5 | **美食偏好沒被真正使用** | 使用者勾了「燒肉」，但系統只是在 fallback 文字寫「參考燒肉」，實際推薦可能完全無關 | `selectedFoods` 只有渲染 fallback 文字時用到，沒有拿來過濾或加權 meals |

### 2.3 使用者體驗層（中優先）

| # | 問題 | 使用者痛點 |
|---|------|-----------|
| U1 | **行程輸出後不能編輯** | 想把Day 2的景點換到Day 3，完全無法操作 |
| U2 | **沒有行程總覽** | 5天行程只能往下滾，不知道整體的景點分佈和密度 |
| U3 | **沒有「鬆散/緊湊」切換** | 家族旅遊想要慢活、朋友旅遊想要趕路，系統只有一種節奏 |
| U4 | **景點卡片資訊過載** | 每個景點同時顯示 Maps + YouTube + 部落格 + 描述 + 票價，使用者不知道看哪個 |
| U5 | **沒有天氣/氣候提示** | 去大阪夏天，沒提醒帶雨具、多喝水 |

### 2.4 數據缺口層（需長期建設）

| # | 問題 |
|---|------|
| D1 | Attractions/Tokyo：22筆景點三連結全缺，哈利波特影城、teamLab Planets等指標景點受影響 |
| D2 | Outlets覆蓋嚴重不足（Tokyo僅4筆），市區大型商場、百貨、藥妝幾乎全缺 |
| D3 | 沒有景點「停留時長」的精準資料，多數是「1-2小時」這種模糊值 |
| D4 | 沒有店鋪「公休日」資料（週二休、節假日休等） |

## 三、升級方案：Phase 1 — 真正以使用者為中心的行程生成

### 3.1 核心概念重構：「路線導向」取代「模板填充」

**現況邏輯**：
```
模板 day1 → 塞入使用者的景點 → 填入5個時段 → 完成
```

**新版邏輯**：
```
使用者輸入（想去哪裡）→ 路線最佳化（不走回頭路）→ 插入用餐 → 加入交通提示 → 完成
```

### 3.2 新增欄位（資料層）

####  attractions 表新增
```sql
ALTER TABLE attractions ADD COLUMN estimated_stay_minutes INTEGER;  -- 精準分鐘數：90, 120, 180
ALTER TABLE attractions ADD COLUMN opening_hour TEXT;             -- "09:00"
ALTER TABLE attractions ADD COLUMN closing_hour TEXT;             -- "18:00"
ALTER TABLE attractions ADD COLUMN closed_days TEXT;               -- JSON: ["星期二"]
ALTER TABLE attractions ADD COLUMN rain_alert TEXT;                -- "室內備案景點"
```

#### meals 表新增
```sql
ALTER TABLE meals ADD COLUMN sub_type TEXT;      -- 'breakfast' / 'lunch' / 'dinner' / 'cafe' / 'snack'
ALTER TABLE meals ADD COLUMN price_range TEXT;    -- '$' / '$$' / '$$$'（以當地幣值計算）
ALTER TABLE meals ADD COLUMN queue_minutes INTEGER; -- 排隊預估分鐘數
ALTER TABLE meals ADD COLUMN sub_category TEXT;   -- '小吃' / '餐廳' / '咖啡' — 已有但要盤點
```

### 3.3 新行程生成演算法

#### 核心：路線串接（Route Builder）

```
輸入：wantItems（使用者指定的景點）+ wantStations + selectedFoods + days

Step 1：景點分組
  → 根據座標（lat/lng）將景點分群（每群代表一個區域，移動時間 < 30分鐘）
  → 每組對應1~2個主要車站

Step 2：每日路線建構
  → 對每一天，先排「早上第一個景點」（從最外圍開始，順時針/逆時針收斂）
  → 每加入一個景點，計算：
      - 移動時間（車站→景點→下一個車站）
      - 抵達時間（上一個景點結束時間 + 移動時間）
      - 下一個景點的最晚可進場時間（closing_hour - estimated_stay）
  → 若移動時間 > 45分鐘，插入「交通過渡」block

Step 3：用餐插入（符合時段 + 多樣性）
  → 早餐（07:00-09:00）：nearby_stations 內的 sub_type='breakfast' 餐廳
  → 午餐（12:00-13:30）：途經路線附近、sub_type='lunch'、不使用者已選過的同類
  → 晚餐（18:00-20:00）：sub_type='dinner'，優先高評測、多連結
  → 每餐最大排隊時間限制（可設定：30分鐘以內）
  → 同一 sub_category 當天不重複

Step 4：交通anchor計算
  → 不是簡單的「找有相同zone的車站」
  → 而是：根據實際路線，計算「在這兩個景點之間最適合換線的車站」
  → 輸出：🚇 從「A站」搭「X線」到「B站」，約XX分鐘

Step 5：節奏標記
  → 每天標注「節奏」：🧘 慢活（每景點間隔>2hr）/ ⚡ 普通 / 🏃 緊湊
```

### 3.4 新增 UI 功能

| 功能 | 說明 |
|------|------|
| **行程總覽地圖** | 用 Leaflet 或 Google Maps API，標注每天的景點順序與路線 |
| **Drag & Drop 編輯** | 可拖曳調整行程項目順序，系統即時重新計算時間 |
| **鬆散/普通/緊湊 切換** | 影響每個景點的 `estimated_stay_minutes` 乘數（0.8x / 1.0x / 1.2x） |
| **同行人數×用餐** | 揪3人以上：系統自動標注「建議預訂」餐廳（`need_reservation=1`） |
| **時間軸視圖** | 橫軸時間（07:00-22:00），縱軸天數，視覺化每天的行程密度 |
| **景點詳情卡** | 點擊景點展開：票價、營業時間、排隊預估、天氣提示、點我收藏 |

## 四、升級方案：Phase 2 — 用餐推薦引擎

### 4.1 用餐推薦評分模型

每個 meal 有一個推薦分數，計算方式：

```
score = base_score
      + food_match_score（符合使用者勾選的用餐習慣）
      + type_variety_bonus（同一天同一sub_category不重複）
      + time_match_score（早餐時段nearby有breakfast店家）
      + link_quality_score（有gmaps+yt+blog三件套 +30%）
      - queue_penalty（排隊>30min -20%）
      - distance_penalty（偏離路線 > 500m -10%）
```

### 4.2 每日期餐原則

```
早餐（07:00-09:00）：
  → 從前一晚住宿附近的車站方圓300m內選 sub_type='breakfast'
  → 便利商店也收錄（需有 name + zone + gmaps）

午餐（12:00-13:30）：
  → 根據「上午景點」到「下午景點」的路線，選 중간（中間點）500m範圍內
  → 避免與昨晚晚餐同一 sub_category

下午茶（14:00-16:00）：
  → 可選 cafe 或 snack，排在两个景点之间

晚餐（18:00-20:00）：
  → 選「下午最後景點」附近 800m 內
  → 優先：$$$ + need_reservation=1（有優雅用餐體驗）
  → 避開與午餐同一 sub_category
```

### 4.3 必吃清單 vs 彈性用餐

```
使用者的 selectedFoods（「燒肉」「壽司」）→ 轉換為 sub_category 查詢
→ 每天至少一餐強制命中使用者的 selectedFoods
→ 其他餐放寬推薦
```

## 五、升級方案：Phase 3 — 使用者掌控感

### 5.1 編輯模式

- 行程生成後，預設為「檢視模式」
- 按「✏️ 編輯行程」切換為「編輯模式」
- 支援：刪除項目、新增項目（從景點庫拖入）、調整順序
- 編輯後即時更新時間軸

### 5.2 收藏功能

- 點擊景點❤️可以「收藏」
- 收藏的景點在下一個新行程中自動優先考慮
- 長期下來系統理解使用者的偏好

### 5.3 行程分享

- 行程生成後，產生一組 URL（行程參數化壓縮）
- 分享給同行者，同行者可以 fork 編輯
- 不需要登入

## 七、規格變更摘要

| 項目 | 現況 | 目標 |
|------|------|------|
| 行程生成邏輯 | 模板填充 | 路線最佳化（lat/lng串接） |
| 用餐推薦 | Zone匹配 | 路線+時段+多樣性+價格+排隊 |
| 景點停留時間 | 「1-2小時」模糊值 | 精準分鐘數 + 開放/關閉時間 |
| 行程調整 | 不可調整 | Drag & Drop + 編輯模式 |
| 同行人數 | 無功能 | 連動餐廳預訂需求提示 |
| 路線視覺化 | 無 | 每日路線地圖 |
| 行程分享 | 無 | URL參數化分享 |
